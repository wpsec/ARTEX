# 源码安全审查

> 改编说明：基于 usestrix/strix 的 `find-security-vulnerabilities-in-code`（Apache-2.0），已翻译并改写为 ARTEX 工作流。

## 1. 确定审查范围

审查前确认用户授权的仓库、分支、目录或变更集，以及语言、入口、信任边界和排除范围。大型仓库优先聚焦用户指定的服务或差异；不得把本地可见的其他目录、凭据或相邻项目视为授权目标。

本 skill 默认只读审查，不修改源码、配置、依赖或数据库。若用户只要求代码审查，不要自行启动对外扫描或访问代码中出现的第三方主机。

## 2. 追踪可验证的风险链

对每个候选问题逐项检查：

1. **可达入口**：指出真实 HTTP/RPC/消息/任务入口或其他可触发路径。
2. **可控输入**：指出用户可控字段及其绑定、解析或反序列化位置。
3. **传播链**：从 source 追踪到 sink，说明鉴权、类型约束、校验、编码或白名单是否有效阻断。
4. **实际影响**：结合当前代码语义说明可能造成的越权、数据暴露、注入、写入或其他具体后果。
5. **可复现证明**：只有在用户授权的环境中以无害方式实际触发并取得证据，才能将问题作为确认漏洞报告。

版本号匹配 CVE、危险函数出现、静态模式命中、代码看起来可控或理论调用链都只是线索；任何一项缺少时不得声称已确认。对不能安全复现的候选点，用 `record_fact` 标为 `inferred`，写清证据、缺失条件和验证限制。

## 3. 敏感信息与验证边界

- 不读取环境变量中的秘密，不打开密钥、凭据或敏感配置文件；若审查中意外遇到秘密，不复制其值，只记录脱敏类型及必要位置。
- 不把真实 token、Cookie、密码、个人数据或完整响应写入 ARTEX 发现、命令、脚本或报告。
- 需要运行验证时，必须有明确授权、专用测试数据和无害证明路径；不得使用删除、持久化、外传、横向移动、反弹 shell 或拒绝服务类 payload。
- 不把依赖扫描、外部漏洞数据库命中或补丁版本比较替代代码路径验证；相关信息只能作为待核查线索。

## 4. ARTEX 结果记录

确认漏洞时使用 `report_finding`，提供受影响入口、关键 source-to-sink 路径、缺失的控制、可复现证据和影响；证据中的敏感值必须脱敏。没有实际触发或影响未成立时使用 `record_fact`，不要创建确认发现。

报告应标明已审查的目录/差异、未审查部分、运行时验证是否完成，以及外部依赖、CI/CD、日志管线等范围限制。所有中间产物遵守 ARTEX 为当前任务提供的工作目录规则。
